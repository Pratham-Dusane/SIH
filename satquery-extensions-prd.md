## 1. Scope, Rules & How to Read This Document

### 1.1 What this document adds

v1 delivers an agentic controller over a registry of remote-sensing specialists: upload one or two rasters, validate them, classify the query, plan a tool sequence, execute, fuse, and emit an auditable trace. That system stays exactly as it is. Nothing here rewrites the controller, the tool contract, the trace, or the evidence pipeline.

What these eleven features add is **reach**: more input paths into the agent (fetched imagery, live district pulls, N-date stacks), more ways to talk to it (drawn annotations, voice, cross-scene recall), more ways to read its output (3D, reports, dashboards), and one way for it to keep working when nobody is watching (monitors). Each one plugs into a contract v1 already exposes.

### 1.2 The independence contract

This is the constraint that shapes every design decision below. Read it before writing any code.

> **A feature is a folder.** `frontend/features/<id>/` and `backend/features/<id>/`. Deleting both folders, removing one import line from a barrel file, and unsetting the feature's environment variables must leave the application building, passing tests, and behaving exactly as it did before the feature existed - with that panel or nav item simply absent.

Four rules enforce it:

1. **No feature imports another feature.** Not the module, not the types, not the components. A lint rule (18.3) fails the build on violation.
2. **Cross-feature interop happens through v1 contracts only** - the tool registry (v1 §8.2), `EvidenceLayer` (v1 §10.3), the scene/query/trace documents (v1 §13.3), and the panel registry (3.1). Never through direct calls.
3. **Interop is always optional and always guarded.** Where two features are genuinely better together (annotations on a multitemporal stack, a report generated by a monitor), the *consuming* feature checks `features.enabled('other')` at runtime and degrades silently to its standalone behaviour when the answer is no. It never assumes.
4. **Only F0 is a shared dependency.** F0 is not a feature; it is the shell - a panel registry, a nav registry, a chat input primitive, an imagery adapter, an offline admin-boundary lookup. It is small, feature-agnostic, and half-present in v1 already. Everything else depends on F0 and on v1. Nothing depends on anything else.

### 1.3 Non-negotiable design rules (extension)

These sit alongside v1 §1.6, which continues to apply in full. Where a rule below extends a v1 rule, the v1 number is given.

1. **Enhancement is never measurement (extends v1 Rule 1 and Rule 4).** F1 may improve what a model or a human *looks at*. Every number - area, fraction, count, index value - is computed from the original raster and its original transform. A super-resolved pixel is a rendering, not an observation, and it never enters a statistic.
2. **Derived imagery declares itself.** Anything fetched (F3, F10, F11), composited, or synthesised carries `provenance` on the scene and is stated in every report and trace that uses it. A cloud-masked median composite is labelled a composite, with its window, never as an acquisition on a date.
3. **Search results are hypotheses, not causes (F6).** No feature asserts causation. Candidate explanations are ranked, scored, sourced, and accompanied by the non-event explanations that would produce the same pixels.
4. **Every new capability keeps the audit path (extends v1 Rule 1 and R11).** Any new analytical capability is registered as a `Tool` in v1's registry, declares `offline_capable`, and appears in the `ExecutionTrace`. No feature answers a user's substantive question outside the agent's traced path.
5. **New chat surfaces inherit grounding.** F3, F5 and F6 add conversational interfaces. All three route through v1's fusion contract and its numeric grounding check (v1 §9.6). A number that appears in a chat bubble is traceable to a tool output or a database row, or it does not appear.
6. **Every feature is off by default.** `FEATURE_<ID>_ENABLED=false` is the shipped default. A feature that is half-built cannot break a demo.

Every feature section below has the same seven subsections, in the same order, so a coding agent can navigate them identically:

## 3. F0 - Shared Substrate

Not a feature. The shell that lets the other eleven be features. Build it once; it is roughly 400 lines and it is the entire reason the rest of this document can claim independence.

### 3.1 Workbench Right Rail

v1 §4.5 specifies a three-pane workspace (canvas, query console, trace drawer). Add a fourth region on the right.

```
+-------------------------------+-------------------+-----+
|                               |  QUERY CONSOLE    |  R  |
|      EVIDENCE CANVAS          |  (chat)           |  A  |
|      (leaflet / canvas)       |                   |  I  |
|                               |  [answer cards]   |  L  |
|      layer controls           |  [composer]       |     |
+-------------------------------+-------------------+     |
|  EXECUTION TRACE (collapsible drawer)             |     |
+---------------------------------------------------+-----+
```

`components/workbench/RightRail.tsx`:
- Collapsed: a 56 px vertical icon strip, one icon per registered panel, with a tooltip on hover and a subtle dot when a panel has unsaved state (e.g. an in-progress annotation).
- Expanded: 360 px panel that pushes the canvas rather than overlaying it, so drawing (F2) and clicking (F7) still hit the right pixels. Width is drag-resizable, 320-560 px, persisted per user.
- Only one panel open at a time. Keyboard: `Alt+1..9` jumps to a panel, `Esc` collapses.
- Panels that are registered but unavailable for the current scene type render as a disabled icon with the gate's `reason` in the tooltip - never hidden. A user who uploaded a single image should be able to see that *Temporal Fetch* exists and why it is offering to help.

**The panel registry is the independence mechanism.**

```typescript
// frontend/lib/registry.ts
export type SceneType = 'SINGLE' | 'CROSS_MODAL' | 'BI_TEMPORAL' | 'MULTITEMPORAL';
export const ALL_SCENE_TYPES: SceneType[] = ['SINGLE','CROSS_MODAL','BI_TEMPORAL','MULTITEMPORAL'];

export interface WorkbenchPanel {
  id: string;                       // 'annotations'
  featureId: FeatureId;             // 'annotation'  -> gated by GET /api/features
  label: string;
  icon: LucideIcon;
  order: number;                    // rail position; features pick from the reserved bands below
  availableFor: SceneType[];
  gate?: (scene: Scene) => { ok: boolean; reason?: string };
  Component: React.ComponentType<{ scene: Scene }>;
}

const panels = new Map<string, WorkbenchPanel>();
export function registerPanel(p: WorkbenchPanel) { panels.set(p.id, p); }

export function panelsFor(scene: Scene, enabled: Set<FeatureId>): WorkbenchPanel[] {
  return [...panels.values()]
    .filter(p => enabled.has(p.featureId))
    .filter(p => p.availableFor.includes(sceneTypeOf(scene)))
    .sort((a, b) => a.order - b.order);
}
```

Reserved `order` bands, so two features never fight over rail position and neither has to know the other exists: F1 `100`, F2 `200`, F3 `300`, F4 `400`, F6 `600`, F7 `700`. Left nav uses the same scheme via `registerNavItem`.

### 3.2 Feature Flags & Capability Discovery

```python
# backend/core/features.py
FEATURE_IDS = ["enhancement","annotation","temporal_fetch","stack","historical",
               "causal","geo3d","voice","reports","monitor","live"]

def enabled(fid: str) -> bool:
    return os.getenv(f"FEATURE_{fid.upper()}_ENABLED", "false").lower() == "true"

def capability_map() -> dict[str, bool]:
    return {f: enabled(f) for f in FEATURE_IDS}

def require(fid: str):
    """Router dependency. A disabled feature's endpoints 404, they do not 500."""
    if not enabled(fid):
        raise HTTPException(404, f"Feature '{fid}' is not enabled on this deployment")
```

Routers mount conditionally, so a feature that is not enabled contributes no routes, no imports, and no startup cost:

```python
# backend/main.py
OPTIONAL_ROUTERS = {
    "enhancement":    "features.enhancement.router",
    "annotation":     "features.annotation.router",
    # ... one line per feature
}
for fid, module_path in OPTIONAL_ROUTERS.items():
    if features.enabled(fid):
        app.include_router(importlib.import_module(module_path).router)
```

`GET /api/features` returns `capability_map()`. The frontend fetches it once at layout mount into a Zustand slice; `panelsFor()` and `navItemsFor()` read it. **This is the only permitted way for one feature to know whether another exists**, and it is only ever used for optional enhancement, never for required behaviour.

### 3.4 Imagery Acquisition Adapter

Three features fetch imagery for an AOI (F3 a historical date, F10 on a schedule, F11 on demand). One adapter, three consumers, zero coupling between them.

```python
# backend/core/imagery/base.py
class Candidate(BaseModel):
    asset_id: str
    collection: str
    acquired_at: str
    cloud_fraction: float | None
    gsd_m: float
    orbit: str | None
    footprint_wgs84: list[float]

class ImageryTile(BaseModel):
    source: str                       # "gee" | "bhoonidhi"
    collection: str                   # "COPERNICUS/S2_SR_HARMONIZED"
    asset_ids: list[str]              # every acquisition that contributed
    acquired_start: str
    acquired_end: str
    composite: bool                   # True => this is not an observation on a date
    cloud_fraction: float | None
    crs: str
    gsd_m: float
    bounds_wgs84: list[float]
    local_path: str                   # GeoTIFF written through core.storage
    provenance: dict                  # everything a report needs to cite this tile

class ImagerySource(Protocol):
    name: str
    def search(self, aoi: BBox, start: str, end: str,
               max_cloud: float | None) -> list[Candidate]: ...
    async def fetch(self, aoi: BBox, selection: list[str] | None,
                    start: str, end: str, *, target_crs: str | None,
                    target_gsd_m: float | None, composite: bool) -> ImageryTile: ...
```

Two implementations. `GEESource` wraps `ee` and reuses v1's `core/gee.py` initialisation - it does not open a second session. `BhoonidhiSource` wraps NRSC's Bhoonidhi catalogue behind the same protocol.

**Honest note on Bhoonidhi.** Bhoonidhi (NRSC/ISRO) requires registered credentials and its programmatic catalogue access is not a documented public REST API of the kind GEE offers. Treat `BhoonidhiSource` as an adapter with a defined interface and a real implementation attempt, but **make GEE the default and the demonstrated path** (`IMAGERY_SOURCE=gee`). Do not build any feature such that it only works if Bhoonidhi access materialises. If the credentials come through, flipping one environment variable is the whole migration; if they do not, nothing above this line is affected.

**Search before fetch, always.** Every consumer calls `search()` and either shows candidates to the user (F3, F11) or logs them (F10) before spending an export. A fetch that silently produces a mystery composite is the single easiest way to make this system untrustworthy.

### 3.5 Offline Admin-Boundary Lookup

Three features need to turn coordinates into place names, or place names into coordinates (F5 "which locations have I inspected", F6 news queries, F11 district search). Do it offline from a bundled dataset - no geocoding API, no rate limit, no network in the eval container.

```python
# backend/core/geo/admin_lookup.py
class AdminUnit(BaseModel):
    unit_id: str            # "IN-MH-PUNE"
    district: str
    state: str
    centroid: tuple[float, float]
    bounds_wgs84: list[float]

class AdminLookup:
    """Point-in-polygon and name search over a bundled India admin-2 boundary file.
    Loaded once into an STRtree at startup; ~780 districts, negligible memory."""
    def __init__(self, path: str = "data/admin/india_districts.geojson"): ...
    def label_for(self, lon: float, lat: float) -> AdminUnit | None: ...
    def labels_for_bbox(self, bounds: list[float]) -> list[AdminUnit]: ...   # AOIs straddle districts
    def search(self, q: str, limit: int = 10) -> list[AdminUnit]: ...        # fuzzy, state-disambiguated
    def geometry(self, unit_id: str) -> dict: ...
```

Source the boundaries from a permissively-licensed dataset (GADM, Natural Earth admin-2, or a Survey of India derivative) and **record the vintage in `data/admin/VERSION`**. Indian district boundaries change - new districts were created in several states in recent years - so a stale file will silently mislabel scenes. Surface the vintage in the F5 dashboard footer and in F9 reports.

`labels_for_bbox` returns a list, not a single unit, because a 100 km² AOI regularly spans two or three districts. Consumers must handle the multi-label case; F6 in particular should query news for every intersecting district, not just the centroid's.

## 4. F1 - Scene Enhancement Preprocessing Layer

### 4.1 Purpose & surface

Insert an enhancement stage between scene ingestion and every downstream consumer, so that a low-resolution, hazy, or radiometrically compressed raster becomes legible to the models and to the analyst. The stage runs on **every scene update** - initial ingest, re-validation, ROI change, and every push onto a temporal stack - not only on first upload.

Surface: right rail panel **Enhancement** (`order: 100`), available for all scene types.

### 4.2 Independence contract

Needs from v1: the ingest pipeline (§6.2-6.6), `Scene`, `ExecutionTrace`. Needs from F0: the right rail.
Must not need: anything else. If F1 is disabled, `enhance()` is never called and v1's `preprocessor.prepare()` receives the raw array exactly as it does today.
Optional interop: F4 calls the same `enhance()` entrypoint per stack member if F1 is enabled; F7 uses the enhanced preview as a terrain texture if it exists. Both check `features.enabled('enhancement')` and fall through to the original raster otherwise.

### 4.3 The rule that governs this entire feature

> **Enhancement is display and perception only. Measurement always runs on the original raster.**

Super-resolution invents plausible high-frequency texture. That is useful for a human eye and for a VLM being asked "is that a bridge", and it is *poison* for anything that produces a number. A 4× upscaled raster has 16× the pixels and exactly the same information; computing area from it and reporting an improved GSD would be a fabricated measurement of the kind v1 §1.6 Rule 1 exists to prevent.

Therefore:
- The enhanced array is written to a **separate artifact** (`derived/enhanced/{method}/{hash}.tif`). The original is never overwritten.
- `ImageMeta.gsd_m` never changes. The enhanced artifact carries `effective_gsd_m` and `is_synthetic_resolution: true`, and every consumer that reports area reads `gsd_m`.
- `spectral_index`, `sar_water_mask`, `geo_stats`, `coreg_check`, `change_detect` and the GEE tools all bind to the original. Only the preview generator and the VLM-facing `model_ready_images()` bind to the enhanced artifact.
- Every trace that ran against an enhanced scene carries an `enhancement` block. A judge reading a trace can always tell whether the pixels a VLM saw were the pixels that arrived.

### 4.4 Method ladder

`services/ingest/enhance.py`. Methods are ordered cheapest-and-safest first; the default configuration stops well short of the hallucinating end.

| `method_id` | What it does | Invents detail? | Offline | Default for |
|-------------|--------------|-----------------|---------|-------------|
| `none` | Pass-through | No | Yes | - |
| `radiometric` | Per-band 2-98 percentile stretch, CLAHE on luminance (clip 2.0, 8×8 tiles), edge-preserving denoise | No | Yes | **all modalities** |
| `pansharpen` | Brovey or Gram-Schmidt fusion of a panchromatic band with the MS bands | No - real resolution | Yes | optical/MS with a pan band |
| `sr_x2` / `sr_x4` | Learned super-resolution (Real-ESRGAN / SwinIR / EDSR via ONNX Runtime) | **Yes** | Yes, weights local | opt-in only |
| `speckle` | Refined-Lee or non-local-means speckle filter on dB-scaled amplitude | No | Yes | **SAR, before anything else** |

**Modality routing is mandatory, not a nicety.** An RGB-trained SR network applied to raw SAR amplitude produces confident garbage: SAR amplitude is right-skewed multiplicative-noise data, not reflectance. The SAR path is always `to_db -> speckle -> (optional) sr -> normalise`, reusing v1 §6.5's dB conversion so there is one dB implementation in the codebase, not two.

**Prefer `pansharpen` over `sr_*` whenever a pan band exists.** Pansharpening moves real information from a real sensor into the MS bands; SR guesses. For Cartosat-2S products in particular this is the difference between a defensible 0.65 m product and a hallucination.

```python
# services/ingest/enhance.py
class EnhancementRecord(BaseModel):
    method: str
    params: dict
    scale: float                      # 1.0 for radiometric/speckle/pansharpen-in-place
    effective_gsd_m: float | None
    is_synthetic_resolution: bool
    quality: dict                     # {"ssim_vs_upsampled":..., "lap_var_before":..., "lap_var_after":...}
    accepted: bool
    rejection_reason: str | None
    artifact_path: str | None
    duration_ms: int
    cache_hit: bool

def enhance(meta: dict, arr: np.ndarray, modality: str,
            cfg: EnhancementConfig) -> tuple[np.ndarray, EnhancementRecord]:
    key = cache_key(meta["checksum"], cfg)
    if (hit := ENHANCE_CACHE.get(key)):
        return hit.array, hit.record._replace(cache_hit=True)

    if modality == "SAR":
        work = speckle_filter(to_db(arr), method=cfg.speckle_method)
    else:
        work = radiometric(arr, clahe_clip=cfg.clahe_clip)
        if cfg.method == "pansharpen" and has_pan_band(meta):
            work = pansharpen(work, meta, algorithm=cfg.pansharpen_algo)

    if cfg.method.startswith("sr_"):
        scale = int(cfg.method[-1])
        work = tiled_sr(work, scale=scale, tile=cfg.tile_px, overlap=cfg.overlap_px,
                        weights=cfg.sr_weights, modality=modality)

    record = quality_gate(original=arr, enhanced=work, cfg=cfg)
    if not record.accepted:
        # Fall back one rung down the ladder, record why, never fail the ingest.
        return radiometric(arr, clahe_clip=cfg.clahe_clip), record
    return work, record
```

**Tiling is required, not optional.** A 4096² raster through a 4× SR network is a 16384² output; naively that is an out-of-memory crash on any laptop. Tile at 256 px with 32 px overlap and blend with a cosine feather across the overlap band. Seam artefacts along tile boundaries are the classic failure here, and a hard-edged seam will be read as a linear feature by both a human and a VLM - feather, do not butt-join. Reuse v1 §6.5's tile-grid bookkeeping so a scene has one tiling story.

**Transform arithmetic for scaled output:**

```python
def scaled_transform(src_transform: Affine, scale: int) -> Affine:
    return src_transform * Affine.scale(1 / scale, 1 / scale)
```

Write it into the enhanced artifact so the file is a valid, openable GeoTIFF that a user can pull into QGIS - but tag it `SATQUERY_SYNTHETIC_RESOLUTION=true` alongside `SATQUERY_SOURCE_GSD_M` so it cannot be mistaken for a real product six months later. This mirrors v1 §10.2's practice of writing the trace id into evidence GeoTIFFs.

### 4.5 Quality gate

SR does not always help, and it sometimes actively hurts (heavy compression artefacts get amplified; low-contrast SAR gets smeared). Do not trust it blindly.

```python
def quality_gate(original, enhanced, cfg) -> EnhancementRecord:
    ref = cv2.resize(original, enhanced.shape[:2][::-1], interpolation=cv2.INTER_CUBIC)
    ssim_val = ssim(ref, enhanced, channel_axis=-1, data_range=1.0)
    lap_before = laplacian_variance(ref)
    lap_after  = laplacian_variance(enhanced)

    accepted, reason = True, None
    if ssim_val < cfg.min_ssim:                  # default 0.70
        accepted, reason = False, (
            f"SSIM {ssim_val:.3f} against bicubic upsample is below {cfg.min_ssim}; "
            "the model is restructuring content rather than sharpening it")
    elif lap_after < lap_before * cfg.min_sharpness_gain:   # default 1.05
        accepted, reason = False, (
            f"No sharpness gain ({lap_after:.1f} vs {lap_before:.1f}); "
            "enhancement is not earning its compute")
    return EnhancementRecord(..., quality={"ssim_vs_upsampled": ssim_val, ...},
                             accepted=accepted, rejection_reason=reason)
```

Two metrics, two failure modes. Low SSIM against a bicubic reference means the network is *changing* the scene, not resolving it - reject. No Laplacian gain means it did nothing at cost - reject and save the compute next time. Both rejections are recorded and shown in the panel, because "we tried and it did not help" is useful information that a silent fallback would throw away.

### 4.6 Cache & idempotency

The stage runs on every scene update, so it must be cheap on repeats.

- Key: `sha256(source_bytes)[:16] + method_id + sorted(params) + weights_version`
- Store: `workspaces/{ws}/scenes/{id}/derived/enhanced/{key}.tif` via `core.storage`, plus the `EnhancementRecord` in the scene document
- Invalidate on: source file change (checksum differs), method or params change, weights version bump
- Concurrency: a per-key lock so two simultaneous updates do not both run a 90 s SR job
- Lifecycle: enhanced artifacts fall under v1 §17.3's `derived/**` 30-day deletion rule and regenerate on demand from the recorded parameters

### 4.7 UI specification

Right rail panel, four blocks:

1. **Method selector** - segmented control (`Off / Radiometric / Pansharpen / SR 2× / SR 4×`), with unavailable options disabled and explained ("no panchromatic band in this scene").
2. **Before/after** - a `react-compare-slider` (already a v1 dependency) over the two previews, with a 4× loupe on hover for pixel-level comparison. This is the only honest way to present SR: let the analyst see exactly what was added.
3. **Quality readout** - SSIM, sharpness gain, output dimensions, effective GSD, duration, cache hit/miss. If the gate rejected, an amber row with `rejection_reason`.
4. **The standing notice**, always visible, never dismissible: *"Enhancement affects display and model input only. All areas, fractions and counts are computed from the original raster at {gsd_m} m."*

Elsewhere in the app: an `Enhanced` chip on the evidence canvas whenever the displayed preview is enhanced, and a corresponding row in the trace drawer header. A user must never be uncertain about which pixels they are looking at.

### 4.8 Failure & degradation

| Condition | Behaviour |
|-----------|-----------|
| Weights missing / ONNX Runtime unavailable | SR options disabled with "super-resolution weights not installed"; radiometric still works |
| Quality gate rejects | Fall back to `radiometric`, record `accepted=false` + reason, show the amber row |
| Raster too large even tiled | Cap at `ENHANCEMENT_MAX_PIXELS`; above it, enhance the preview only (not the analysis array) and say so |
| Enhancement raises | Log, return the original array, mark the record `FAILED`; **ingest never fails because enhancement failed** |
| Scene is `benchmark_mode` PNG | Radiometric only; SR is refused so benchmark inputs are never altered before scoring |

- [ ] All five methods implemented with correct modality routing; SAR never sees an RGB SR network
- [ ] Tiled SR with feathered blending; no visible seams on a 4096² test raster

- [ ] Cache hit on an unchanged re-validate (assert `duration_ms < 50`)
- [ ] `geo_stats` on an enhanced scene returns the **same** hectares as before enhancement (regression test - this is the rule in 4.3 made executable)
- [ ] `enhancement` block present in the trace; `Enhanced` chip on the canvas
- [ ] With the feature disabled, ingest byte-compares identically to v1

## 5. F2 - Layered Annotation & Agent Annotation Protocol

Four subheadings, one feature. They are not separable: an annotation the agent cannot read is a drawing tool, and an agent answer the user cannot see as a mark on the image is just more text.

### 5.1 Purpose & surface

Give the user a Photoshop-style layered vector annotation system over the scene imagery, make those annotations legible to the agent as structured input, and let the agent reply *in the same medium* - producing its own removable, colour-coded layers for answers like "where is the water".

Surface: right rail panel **Annotations** (`order: 200`), available for all scene types.

### 5.2 Independence contract

Needs from v1: the evidence layer contract (§10.3), the tool registry (§8), `preview_meta` + `pixelToLatLng` (§6.6), the canvas (§4.5). Needs from F0: the right rail.
Must not need: F4. If a scene is multitemporal, annotations bind to whichever member is active by id; if F4 is absent, that id is simply one of `single|optical|sar|t1|t2`.
Optional interop: F4 (`targetImageRole` accepts a stack member id, and a layer may target `*` = all members); F7 (drape a layer onto terrain).

---

#### 5.3 (A) Canvas & layer model

**Data model.** Vector, not raster. Storing strokes as geometry rather than pixels is what makes everything downstream possible - erasing is removing a shape, rescaling is free, and the geometry converts to GeoJSON and to a boolean mask on demand.

```typescript
export type AnnotationKind =
  | 'freehand' | 'polygon' | 'rect' | 'ellipse' | 'arrow' | 'point' | 'text';

export interface AnnotationShape {
  id: string;
  kind: AnnotationKind;
  points: [number, number][];    // NORMALISED image coords, [0,1] x [0,1], origin top-left
  colour: string;                // hex; inherits the layer colour unless overridden
  strokeWidth: number;           // px at 1:1 preview scale, 1-24
  filled: boolean;
  fillOpacity: number;           // 0-1
  label?: string;                // shown as a badge; also read by the agent
  text?: string;                 // for kind === 'text'
}

export interface AnnotationLayer {
  id: string;
  sceneId: string;
  name: string;                  // "Layer 3" or user-renamed; the agent reads this
  author: 'user' | 'agent';
  sourceQueryId?: string;        // agent layers only - links back to the answer
  sourceTool?: string;           // agent layers only - e.g. 'sar_water_mask'
  targetImageRole: string;       // 'single'|'optical'|'sar'|'t1'|'t2'|<stackMemberId>|'*'
  colour: string;
  visible: boolean;
  locked: boolean;
  opacity: number;
  zIndex: number;
  shapes: AnnotationShape[];
  createdAt: string;
  updatedAt: string;
}
```

**Why normalised image coordinates are the canonical form.** Three coordinate spaces are in play: screen pixels (changes with zoom and window size), source raster pixels (changes if F1 super-resolves), and geographic coordinates (do not exist for benchmark PNGs). Normalised image coordinates are stable under all three. They survive enhancement, they survive preview regeneration at a different long-edge size, they work in `benchmark_mode`, and they convert to either of the other two spaces with one multiplication. v1 §6.6 already ships `preview_meta.json` and `pixelToLatLng` for exactly this mapping, which is why the user's instinct to reuse "the coordinate system of images we already have" is the right one.

Geographic coordinates are **derived, not stored as truth**: when `scene.georeferenced`, every shape gets a `geo` GeoJSON member in EPSG:4326 computed on write, so annotations round-trip to QGIS and so the agent can talk about latitude. When the scene is not georeferenced, `geo` is absent and every downstream consumer reports position in normalised coordinates and compass terms only.

**Rendering.** An SVG overlay layer above v1's `ImageOverlay`, inside the same Leaflet pane stack as evidence layers so z-ordering is coherent (base image -> secondary -> masks -> change map -> **annotations** -> boxes -> labels). In `benchmark_mode` the identical SVG is absolutely positioned over the canvas viewer. One component, one branch on `scene.georeferenced`, exactly as v1 §4.5 does for the canvas itself.

**Panel controls.**

- **Tool row**: freehand pen, polygon (click to place, double-click/Enter to close), rectangle, ellipse, arrow, point marker, text label, select/move, eraser (deletes a whole shape - vector, not pixel), pan. Active tool highlighted; `V/P/G/R/E/A/T/X` shortcuts.
- **Colour section**: an 8-swatch colour-blind-safe palette plus a custom hex input. A new layer auto-claims the next unused palette colour, so two layers are never accidentally the same colour. Swatches show a used/unused indicator.
- **Pen width section**: slider 1-24 px with a live-rendered dot preview at the chosen width and colour. Width is per-shape, seeded from the current tool setting.
- **Fill**: toggle + opacity slider for closed shapes.
- **Layer list**: drag to reorder (sets `zIndex`), eye toggle, lock toggle, colour chip, shape count, inline rename on double-click, per-layer opacity slider, duplicate, merge-down, delete. Multi-select with `Shift`. Agent layers carry an `AI` badge and a dashed stroke preview.
- **Undo/redo**: 50-deep per scene, `Cmd+Z` / `Cmd+Shift+Z`, covering shape creation, deletion, move, and layer operations.
- **Attach to agent**: a prominent button that adds selected layers to the composer as a `contextChip` ("2 layers attached"), which is how 5.5 gets its input.
- **Import / Export**: GeoJSON both ways (georeferenced scenes) and a normalised-coordinate JSON for benchmark scenes.

**Colour coding, with a second channel.** Colour distinguishes layers, but colour alone is a bad sole channel - roughly 1 in 12 men have some colour-vision deficiency, and printed reports (F9) are often greyscale. So: **solid stroke = user, dashed stroke = agent**, plus a numeric badge on every shape (`1`, `2`, `3`...) that is also what the agent refers to in text. A user reading a greyscale PDF can still follow "the vegetation loss is concentrated in region 2".

**Autosave** on a 800 ms debounce; explicit save on blur. Never lose a drawing to a page refresh.

One conversion module, `services/annotation/geometry.py`, used by every consumer so there is exactly one implementation of each transform:

#### 5.5 (C) Agent comprehension of user annotations

An annotation reaches the agent in **three complementary forms**, because three different kinds of consumer need three different things. All three derive from the same layer, so they cannot disagree.

**Form 1 - symbolic (for the planner and deterministic tools).** The `describe()` block above, injected into the planner payload as `annotations: [...]` alongside the existing scene metadata. The planner uses it to decide *which* tools to run and to bind mask references.

**Form 2 - raster mask (for measurement).** Each attached layer is rasterised and registered as an artifact under the key `annotation:{layer_id}`, available to any `mask_ref` parameter. This is the highest-value part of the feature, because it turns a drawing into a measurement scope:

> *"How much of what I circled is vegetation?"*
> `spectral_index(index=NDVI)` -> `geo_stats(mask_ref="annotation:lyr_7c1a", units="ha")`

The answer is fully deterministic, fully grounded, offline-capable, and exact. No VLM is asked to judge what is inside a circle; the circle is a mask and the index is arithmetic.

**Form 3 - visual burn-in (for the VLM tools).** For `rs_vqa`, `rs_caption`, `change_describe` and `change_vqa`, render the attached layers onto a copy of the (possibly F1-enhanced) preview: stroke in the layer colour, plus a filled numeric badge at each shape's centroid. Prepend a legend to the instruction:

```
The image contains 2 user annotations, drawn over the imagery:
  [1] cyan polygon, "suspected breach", south-west quadrant, 2.1% of the frame
  [2] amber arrow, from centre-north pointing south-southeast, 1.18 km long
Refer to annotated regions by their number. Answer only about what is visible.
```

Drawing the mark *and* naming it is what makes this reliable. A VLM asked "what is in the red circle" on an unlabelled image frequently answers about the wrong region; the same model given a numbered badge and a legend that states the number, colour and quadrant is substantially more consistent. Note honestly in `confidence_basis` that this remains a hosted, unadapted VLM (v1 §7.0) - burn-in improves reference resolution, it does not make the model a remote-sensing expert.

**Classifier and planner integration.** Add to v1 §9.2:

```python
ANNOTATION_CUES = ("this region", "this area", "the circled", "the marked", "the highlighted",
                   "inside the", "within the", "what i drew", "my annotation", "the polygon",
                   "region 1", "region 2", "here")
```

When cues match *or* layers are attached to the request, the rule planner (v1 §9.4) prepends `annotation_stats` and rewrites downstream `mask_ref` parameters to the annotation artifact key:


**Optional ROI promotion.** A single closed layer can be promoted to the scene ROI with one click, reusing v1's existing `POST /api/scenes/{id}/roi` (§12.2) so all subsequent tools crop to it. Offered as a button, not done automatically - the mask-reference path is more precise (arbitrary polygons vs v1's rectangle) and is the default.

**New tool** - registered in v1's registry like any other, so it inherits the trace, confidence and parameter whitelisting for free:

```python
class AnnotationStatsParams(ToolParams):
    layer_ids: list[str] = Field(min_length=1, max_length=12)
    units: Literal["m2","ha","km2","percent"] = "ha"

@register
class AnnotationStatsTool(Tool):
    name = "annotation_stats"
    description = ("Measure user- or agent-drawn annotation regions: area, perimeter, "
                   "centroid, bounding box, and geographic position. Use this before any "
                   "analysis that is scoped to a drawn region.")
    accepts = ["SINGLE", "CROSS_MODAL", "BI_TEMPORAL", "MULTITEMPORAL"]
    required_modalities = []
    params_model = AnnotationStatsParams
    produces = ["stats", "mask"]
    model_id = None
    offline_capable = True

    async def run(self, ctx, p: AnnotationStatsParams) -> ToolResult:
        facts, artifacts = {}, {}
        for lid in p.layer_ids:
            layer = ctx.annotation(lid)
            mask = to_mask(layer, ctx.width, ctx.height)
            artifacts[f"annotation:{lid}"] = ctx.store_mask(mask)
            facts[lid] = {**describe(layer, ctx.scene),
                          "area": mask_area(mask, ctx.gsd_x_m, ctx.gsd_y_m, p.units)}
        return ToolResult(tool=self.name, facts=facts, artifacts=artifacts,
                          text=render_annotation_summary(facts), confidence=1.0,
                          confidence_basis="exact vector geometry; no estimation involved")
```

Confidence is 1.0 and honestly so - the geometry is exactly what the user drew. Note that v1 §9.7's `TOOL_WEIGHTS` gives deterministic tools a low weight precisely because they are near-certain but low-information; add `"annotation_stats": 0.2` in that spirit.

#### 5.6 (D) Agent-authored annotations

The agent answers *in annotations*, not only in text. "Where is the water" returns a cyan polygon layer named "Water (NDWI > 0, Otsu)" that appears in the same layer list the user draws into, and that the user can hide, recolour, or delete.

**The critical design decision: agent annotations are derived from measurements, not drawn by a model.** The `annotate` tool has a strict preference order:

```python
class AnnotateParams(ToolParams):
    target: str                                    # "water", "the reservoir", "changed area"
    source_artifact: str | None = None             # prefer an existing mask from a prior step
    simplify_tolerance_px: float = Field(2.0, ge=0.0, le=32.0)
    max_regions: int = Field(20, ge=1, le=200)
    min_area_fraction: float = Field(0.0005, ge=0.0, le=0.5)

@register
class AnnotateTool(Tool):
    name = "annotate"
    description = ("Draw the answer on the image as a removable annotation layer. "
                   "Prefer to convert a mask produced by a measurement tool; only fall back "
                   "to model-proposed boxes when no measurement tool can produce the region.")
    produces = ["annotation", "geojson"]
    offline_capable = True          # when fed a mask; the fallback path is not
```

Preference order inside `run()`:

1. **A mask artifact from a prior step** (`sar_water_mask`, `spectral_index`, `change_detect`, `sar_optical_fuse`, `rs_classify`) -> `rasterio.features.shapes` -> `shapely.simplify(tolerance=gsd_m/2)` (matching v1 §10.2) -> drop regions below `min_area_fraction` -> polygons. **This is a measured answer rendered as a drawing.**
2. **Boxes from `rs_ground`** -> rectangle shapes, with the VLM's honest confidence caveat carried into the layer name.
3. **Nothing.** If neither exists, return `confidence=0.0` and the text "No region matching '{target}' could be located", exactly as v1 §7.1 requires of `rs_ground`. **The tool never asks a language model to invent coordinates for a shape.**

The planner appends `annotate` whenever the query has grounding cues (v1's existing `GROUNDING_CUES`) and a mask-producing step is already in the plan - which is most of the time, since v1's planner already schedules measurement before description.

**Rendering and provenance.** Agent layers use v1 §10.1's semantic evidence palette so colour meaning is consistent across the product (water `#38bdf8`, change `#ef4444`, built-up `#f59e0b`, vegetation `#a3e635`, cross-sensor conflict `#a855f7`), drawn with a dashed stroke and an `AI` badge. Each carries `sourceQueryId` and `sourceTool`, so clicking it scrolls the query console to the answer that produced it - and clicking the answer card flashes the layer. This extends v1 §4.5's existing two-way evidence-text linking rather than inventing a parallel mechanism.

**Evidence contract extension.** Add `'annotation'` to v1 §13.1's `EvidenceLayer.type` union with an `annotationLayerId` member. Because v1 §10.3 promises that "adding a tool that produces one of these needs zero frontend changes", this is the only frontend change the agent-authoring path requires.

### 5.7 Data & API

Firestore: `annotations/{layerId}` scoped by `scene_id` and `workspace_id`. Full model in 15.2, endpoints in 16.2.

## 6. F3 - Single-to-Bitemporal Promotion

### 6.1 Purpose & surface

A user has one image and wants a delta. They do not have the second observation, and acquiring one is exactly the kind of GIS chore this product exists to remove. F3 lets them ask - *"what's the difference between this and the same location in 2025?"* - extracts the AOI from the image they already uploaded, fetches the matching observation from a public catalogue, and promotes the pair into a standard bi-temporal scene that the existing agent can answer over.

Surface: right rail panel **Temporal Fetch** (`order: 300`), available only for `SINGLE` scenes.

### 6.2 Independence contract

Needs from v1: `Scene.images[].bounds_wgs84` and CRS (§6.2), the compatibility checker (§6.4), the standard ingest path, and `POST /api/query`. Needs from F0: right rail, `ChatComposer`, `ImagerySource`.
Must not need: F4. F3's output is a plain `BI_TEMPORAL` scene, which v1 already fully supports.
Optional interop: if F4 is enabled, the panel additionally offers "add to stack" instead of "create pair", pushing the fetched date onto an existing multitemporal stack. Guarded by `features.enabled('stack')`.

**F3 adds no reasoning.** It acquires imagery and hands off. Every question the user asks is answered by v1's controller running on the derived scene. This is deliberate: duplicating change-detection logic inside a fetch feature is how two divergent answers to the same question get shipped.

### 6.3 Flow

```
[1] gate        SINGLE + georeferenced? else structured refusal
[2] parse       natural-language date/intent -> TemporalFetchRequest   (rules first, LLM fallback)
[3] preflight   ImagerySource.search() -> candidate acquisitions, shown to the user
[4] select      user picks an acquisition (or accepts the recommended one)
[5] fetch       async export, clipped to the AOI, reprojected to the source CRS
[6] promote     new BI_TEMPORAL scene, members ordered by acquisition date
[7] validate    v1 compatibility checker runs; report shown before any query
[8] answer      the user's original question is submitted to POST /api/query on the new scene
```

### 6.4 Gate

The panel is disabled with an explanatory reason unless **both** hold:

- `scene.input_config === 'SINGLE'`
- `scene.georeferenced === true`

The second is not negotiable. A `benchmark_mode` PNG has no CRS, therefore no bounds, therefore no AOI, therefore nothing to fetch. Render v1's structured-refusal treatment (§4.5 `AbstentionNotice`): what was asked, why it cannot be done, and the concrete remedy ("upload the GeoTIFF version of this image, which carries the geographic bounds needed to look up the same area").

### 6.5 Intent parsing

Deterministic first, model second - the same inversion v1 §9.2 argues for, and for the same reason: this is a low-entropy parse and rules are faster, free, offline and auditable.

**Modality matching.** `collection_hint='auto'` resolves to the modality of the uploaded image: an optical upload fetches Sentinel-2, a SAR upload fetches Sentinel-1 GRD. This is not a preference - v1 §6.4's compatibility checker flags mismatched modalities in a bi-temporal pair as a `WARN` because optical-vs-SAR differencing is not a change signal, it is a sensor difference. Fetch the matching sensor and the derived scene passes cleanly.

### 6.6 Preflight and selection

Never fetch blind. `ImagerySource.search()` returns candidates and the panel renders them as a selectable list:

| Date | Cloud | Tile / orbit | Days from target | |
|------|-------|--------------|------------------|---|
| 2025-03-14 | 4% | T43QFV | +2 | **recommended** |
| 2025-03-09 | 31% | T43QFV | -3 | |
| 2025-03-24 | 68% | T43QFV | +12 | cloudy |

Recommendation ranking: cloud fraction first, then temporal distance from target, then footprint coverage of the AOI. Also offer a **composite** option ("cloud-masked median over March 2025") which is often the only way to get a usable optical image in a monsoon month - but label it, and set `ImageryTile.composite=true` so extension Design Rule 2 carries the label through to the scene, the trace and every report. A composite is a statistic over a window, not an observation on a date, and a change detection against one has a different meaning. Say so in the UI once, at the point of choice.

### 6.7 Fetch and promotion

```python
async def fetch_and_promote(scene: Scene, req: TemporalFetchRequest,
                            selection: list[str] | None) -> Scene:
    src = scene.images[0]
    aoi = BBox(*src.bounds_wgs84)

    tile = await imagery.fetch(
        aoi, selection, req.target_start, req.target_end,
        target_crs=src.crs,                     # reproject to the user's CRS, not ours
        target_gsd_m=comparison_gsd(src),       # see below
        composite=req.composite,
    )

    t_src, t_new = src.acquired_at, tile.acquired_start
    earlier, later = sorted([(t_src, src), (t_new, tile)], key=lambda x: x[0] or "")

    return create_scene(
        workspace_id=scene.workspace_id,
        name=f"{scene.name} vs {tile.acquired_start[:10]}",
        input_config="BI_TEMPORAL",
        images=[as_image(earlier[1], role="t1"), as_image(later[1], role="t2")],
        derived_from=scene.id,
        provenance={"kind": "temporal_fetch", "source_scene": scene.id, **tile.provenance},
    )
```

**Ordering is by acquisition date, not upload order.** If the user asks for 2019 and their upload is from 2024, the fetched image becomes `t1` and the upload becomes `t2`. Getting this backwards inverts the sign of every change statement the agent makes, which is the single worst bug available in this feature. Assert it in a test.

**The GSD problem, and the honest fix.** A Cartosat-2S upload at 2 m against a Sentinel-2 fetch at 10 m gives a GSD ratio of 5. v1 §6.4's checker grades ratio > 4.0 as `FAIL`, which blocks querying entirely - correctly, for two arbitrary uploads. But here the mismatch is *known, expected and structural*, not a user error.

Handle it explicitly rather than by relaxing the gate:

```python
def comparison_gsd(src: ImageMeta) -> float:
    """Both members are resampled to the coarser GSD before comparison.
    Comparing 2 m against 10 m at 2 m manufactures detail on one side only."""
    return max(src.gsd_m, CATALOG_GSD[src_collection])
```

Then set `scene.comparison_gsd_m`, tag the derived scene `resolution_matched=True`, and add a `WARN`-level compatibility row reading *"members resampled from 2.0 m and 10.0 m to a common 10.0 m grid for comparison; fine-scale change below 10 m is not detectable in this pair."* Cap aggregate confidence for queries on this scene at `0.7` in v1 §9.7's aggregation, the same way a misregistration warning caps it. The user gets their answer, correctly hedged, instead of a hard block or a false precision.

**Async execution.** GEE exports take 30 s to several minutes. Return a job id immediately, poll, and stream progress states (`SEARCHING -> QUEUED -> EXPORTING -> DOWNLOADING -> INGESTING -> VALIDATING -> READY`) into the panel. Reuse v1's Cloud Tasks path where deployed; a local thread pool is sufficient in dev.

### 6.8 The chat surface

`ChatComposer` with `suggestions`:
- "What's different between this image and the same area in 2025?"
- "Show me this location before the 2023 monsoon"
- "Has the built-up area grown since 2020?"

On submit, the panel runs steps 2-7, then submits the user's original `question` verbatim to `POST /api/query` against the **new** scene, and renders the streamed answer inline in the panel with a "open full workspace" link to `/scene/{newId}`. The conversation reads as one continuous exchange; underneath, a scene was created and v1's controller answered normally, with a full trace.

## 7. F4 - Multitemporal Scene Stack

### 7.1 Purpose & surface

Generalise the bi-temporal pair to an ordered stack of N observations of the same area, uploaded through an animated stack interface where the bottom card is the oldest and the top card is the newest. Everything the user already knows about layers - visibility, opacity, reorder, remove - applies to stack members.

Surface: the upload wizard (a fourth input-mode tab) and right rail panel **Stack** (`order: 400`).

### 7.2 Independence contract

Needs from v1: the ingest pipeline, the compatibility checker (§6.4), `change_detect` / `change_describe` / `change_vqa` (§8.3.4-8.3.6), `InputModeTabs` (§4.4). Needs from F0: right rail.
Must not need: F1, F2, F3.
Optional interop: F1 (each member is enhanced on push if enabled); F2 (a layer binds to a member id, or `*` for all); F3 (a fetched date pushes onto the stack).

### 7.3 The compatibility decision that keeps everything else working

> **`BI_TEMPORAL` is not replaced. It is `MULTITEMPORAL` with N = 2, and it stays on disk as `BI_TEMPORAL`.**

v1's change tools declare `accepts = ["BI_TEMPORAL"]`. Rewriting every scene to a new config would break all of them and would force this feature to touch v1's tool registry, its input gate, its task requirements table and its planner - which is the opposite of independence.

Instead:
- A stack with exactly 2 members persists `input_config: "BI_TEMPORAL"` and is, byte for byte, a v1 bi-temporal scene. Every v1 tool runs on it unchanged.
- A stack with N > 2 persists `input_config: "MULTITEMPORAL"` and is **a scheduler over v1's bi-temporal tools**: multitemporal analysis is implemented as repeated pairwise calls on `(member[i], member[i+1])` or on a user-selected pair, each of which is a plain bi-temporal execution with its own trace steps.

This is not a workaround. Pairwise-with-a-reference is how change analysis over a time series is actually done, and it means every interval in a trajectory is individually auditable rather than emerging from an opaque N-way model.

Cap: `2 <= N <= 12` (`STACK_MAX_MEMBERS`). The reason for the cap is concrete - pairwise change over N members is N-1 GEE-backed executions, and 12 already means a minute-scale job and a real quota cost. State the cap in the UI when the user tries to exceed it.

### 7.4 Data model

```typescript
export interface StackMember {
  id: string;                  // 'mem_01' - stable; annotations and layers bind to this
  order: number;               // 0 = oldest = bottom of the visual stack
  role: string;                // 't1'..'tN', derived from order, kept for v1 tool compatibility
  acquiredAt: string;          // REQUIRED - the ordering key
  dateSource: 'metadata' | 'filename' | 'manual';
  image: ImageMeta;            // v1's ImageMeta, unchanged
  visible: boolean;
  opacity: number;
  enhancement?: EnhancementRecord;   // present only if F1 is enabled
}

export interface TemporalStack {
  members: StackMember[];      // always sorted by acquiredAt ascending
  referenceId: string;         // default: the newest member
  comparisonGsdM: number;      // the coarsest member's GSD; all comparisons run here
}
```

**Order is derived from `acquiredAt`, never from drag position.** Manual reordering is deliberately not offered, because a stack whose visual order contradicts its temporal order will produce change statements with inverted signs. If a member has no date in its GeoTIFF tags, the uploader tries the filename (`S2A_20240317_...`, `LC08_..._20240317`) and otherwise shows an amber **date required** state on that card with an inline date picker. Members without a date are held out of analysis until dated - never defaulted to "now".

### 7.5 The animated stack uploader

A fourth tab in v1 §4.4's `InputModeTabs`: **Multi-Temporal Stack**.

**The interaction.** A single drop zone accepts many files at once. Each accepted file becomes a card that animates into a perspective stack:

```css
/* the container */
transform: perspective(1400px) rotateX(52deg);
transform-style: preserve-3d;
/* each card, i from 0 (oldest, bottom) to n-1 (newest, top) */
transform: translateZ(calc(var(--i) * 18px)) translateY(calc(var(--i) * -10px));
```

Cards land with a framer-motion spring (`stiffness 260, damping 24`, already a v1 dependency), newest settling on top, with a brief highlight ring on the card that just landed. Each card shows a thumbnail, a date chip, a modality chip, GSD, and an ingest progress ring that fills as v1's pipeline runs on that member.

**Controls:**
- **Fan** (hover or press-and-hold) - cards spread along an arc so all N are readable at once
- **Explode** (toggle) - flattens to a date-ordered grid for bulk operations
- **Timeline scrubber** - a horizontal axis positioned by real acquisition date, not by index, so a stack with a three-year gap and a two-week gap *looks* like one. Dragging the playhead brings that member to the front on the canvas.
- **Remove** - X on any card, with the stack restacking in a spring transition
- **Add more** - the drop zone stays live; a late arrival animates into its correct temporal position rather than the top, which is a small detail that teaches the ordering rule better than any tooltip

**Accessibility, and it is not optional here.** Respect `prefers-reduced-motion`: when set, render the identical stack as a plain vertical date-ordered list with no transforms and no springs. The 3D presentation must never be the only way to understand or operate the stack - the same reorder, remove and date-edit actions are available from the list view and by keyboard (`Up/Down` to move focus, `Delete` to remove, `Enter` to open the date editor).

### 7.6 Compatibility for N members

Running v1's pairwise checker across all N² pairs produces an unreadable report and wastes time. Instead:

- Every member is checked **against the reference member** (default: newest; user-changeable from the panel). This gives N-1 check rows, each in v1's existing `CompatibilityCheck` shape, rendered as one row per member in a table.
- The stack's verdict is the worst member verdict. A single `FAIL` member is **excluded from analysis and marked, not allowed to block the whole stack** - a nine-member time series should not be dead because one image is misregistered. Excluded members render greyed with the failing check named on the card.
- `comparisonGsdM` is the coarsest included member's GSD; all pairwise runs resample to it, with the same reasoning and the same WARN text as F3 §6.7.

### 7.7 Stack-aware tools

Three new tools, all registered in v1's registry, all appearing in the trace like any other:

```python
class StackTrajectoryParams(ToolParams):
    metric: Literal["ndvi_mean","ndwi_mean","ndbi_mean","backscatter_mean","water_fraction"]
    mask_ref: str | None = None          # accepts 'annotation:{id}' when F2 is installed
    member_ids: list[str] | None = None  # default: all included members

@register
class StackTrajectoryTool(Tool):
    """Per-member index value over the AOI or a masked region -> a time series.
    Fully deterministic; this is the tool that answers 'is it getting greener'."""
    name = "stack_trajectory"
    accepts = ["MULTITEMPORAL"]
    produces = ["stats"]
    offline_capable = True
```

| Tool | What it does | Offline |
|------|--------------|---------|
| `stack_trajectory` | One index value per member -> time series + slope + turning points | Yes |
| `stack_pairwise_change` | Runs v1 `change_detect` on consecutive (or selected) pairs -> changed fraction per interval, each with its own trace step | No (GEE) |
| `stack_summarize` | VLM description **grounded on the two tools above's facts**, never on the raw series | No |

`stack_summarize` receives the numbers, not the images, for the trend claim - v1 §9.6's numeric grounding check then verifies that every figure in the sentence "vegetation declined steadily from 2019 to 2022 before recovering" traces to a `stack_trajectory` fact. The images still go to the VLM for descriptive content, but the trend is arithmetic.

**Planner integration.** Add to v1 §9.2 a `MULTITEMPORAL` branch mirroring the existing `BI_TEMPORAL` one:

```python
if cfg == "MULTITEMPORAL":
    if any(c in q for c in TREND_CUES):        # "trend", "over time", "progression", "since", "each year"
        t = TaskType.TEMPORAL_TREND
    elif any(c in q for c in ("map", "where exactly")):
        t = TaskType.CHANGE_MAP                 # scoped to the selected pair
    else:
        t = TaskType.CHANGE_VQA                 # answered pairwise against the reference
```

New `TaskType.TEMPORAL_TREND = "TEMPORAL_TREND_ANALYSIS"`, added to v1 §9.3's `TASK_REQUIREMENTS` with `{"configs": ["MULTITEMPORAL"], "modalities": []}`. When the user's question names two specific dates, the planner resolves them to member ids and runs a plain bi-temporal plan on that pair - the ordinary path, unchanged.

### 7.8 Panel and canvas

**Stack panel** (right rail):
- Member list, newest first, each with: thumbnail, date, modality chip, eye toggle, opacity slider, "set as reference" radio, exclude toggle, remove
- Blend mode selector for the top visible member: `normal | difference | multiply`. **Difference blend across two members is the cheapest change visualisation in the product** - no model, no GEE call, instant, and it makes registration error obvious to the eye
- Trajectory chart (Recharts line, from `stack_trajectory`) with the metric selector; clicking a point jumps the canvas to that member
- **Temporal playback**: play/pause, speed (0.5×/1×/2×), loop. Steps the canvas through members at 500 ms each. With `stack_pairwise_change` results present, the change mask for each interval flashes on during the transition. This is the demo shot for this feature
- Per-interval change table: `t_i -> t_{i+1}`, changed %, area (ha), confidence, "view this pair" link that opens the pairwise trace

**Canvas**: members are layers in v1's existing layer stack, so `LayerControls` (§4.5) picks them up with no special-casing. If F2 is installed, annotation layers bound to a member show and hide with that member; layers bound to `*` are always shown.

### 7.9 Failure & degradation

| Condition | Behaviour |
|-----------|-----------|
| Fewer than 2 members | Not a stack; the wizard blocks Confirm with "add at least one more acquisition" |
| More than `STACK_MAX_MEMBERS` | Reject the extra files with the count and the reason; the accepted ones still ingest |

## 8. F5 - Historical Scenes & Cross-Scene RAG

Two subheadings: an analytics dashboard, and a retrieval assistant that answers questions spanning every scene the workspace has ever analysed. They are one feature because they read the same corpus and because the chat answers are far more useful when the user can click a citation and land on the chart that proves it.

### 8.1 Purpose & surface

v1 answers questions about *one scene*. Nobody has ever answered "which locations have I inspected so far?" because no surface in the product looks across scenes. F5 is that surface: a reports-style dashboard with charts, and a chat rail on the right that answers recall and aggregate questions over the entire workspace history.

Surface: left nav **Historical Scenes** (`order: 250`, between *Scene* and *Backend Registry*), route `app/historical/page.tsx`.

### 8.2 Independence contract

Needs from v1: the `scenes`, `queries` and `traces` collections (§13.3) - **read-only, as they already exist**. Needs from F0: left nav, `ChatComposer`, `AdminLookup`.
Must not need: F9. Both aggregate across scenes, and both read v1's collections directly rather than sharing a new store, so neither imports the other.
Optional interop: if F9 is enabled, a "Export this view as PDF" button appears in the dashboard header, calling F9's report API with the current filter state. Guarded.

**No new source of truth.** F5 never writes a scene fact. The only thing it writes is a derived index (8.5), which is rebuildable from the collections at any time and whose loss costs nothing but a reindex.

### 8.3 Layout

```
|  FILTERS  [date range] [config] [modality] [status]|  RAG ASSISTANT   |
```

The chat rail is fixed at 380 px on the right (collapsible), matching the user's expectation and mirroring the workbench's own console-on-the-right arrangement so the product has one spatial grammar.

### 8.4 (A) Analytics dashboard

**Charting library.** Use Recharts - it is already a v1 dependency (§2.1) and it is what the benchmarks page uses, so the product has one chart aesthetic. Every chart below is a pure function of one typed payload from `GET /api/analytics/overview`, so swapping the library later is a presentation change and touches no data code.

**KPI row** (four cards, matching v1 §4.3's dashboard treatment): Scenes analysed · Queries answered · Mean confidence (coloured by v1's `confidence.*` tokens) · Abstention rate (with v1's tooltip explaining that abstention is a feature, not a defect).

**Charts:**

|---|-------|------|------------------------|
| 1 | Coverage map | Leaflet with scene footprint rectangles, coloured by input config, clustered when dense | This is the honest answer to "which locations have I inspected". A list of district names is the text form; the map is the one that gets read |

The dashboard footer states the boundary dataset vintage from `data/admin/VERSION`, because a scene labelled with a district that has since been split needs that context.

### 8.5 (B) Cross-scene RAG assistant

**The design insight that makes this work: two retrieval paths, not one.**

Most questions a user actually asks of their own history are **aggregate or filter** questions - "which locations have I inspected", "how many bi-temporal scenes did I run in March", "which scene had the largest changed area", "have I ever looked at Nashik". Vector similarity search answers these badly: embeddings retrieve *topically similar* documents, and "which locations" has no topic. Meanwhile genuinely semantic questions - "what did the agent say about flooding near the reservoir" - are answered badly by SQL.

So the router picks, and when it is unsure, it runs both.

```
question
   |
   v
[ROUTER]  rules first (aggregate verbs, count words, filter phrases), LLM fallback
   |
   +--> PATH A  structured   -> compile to AnalyticsQuery -> execute against the DB
   |                            -> exact rows, exact counts, exact totals
   |
   +--> PATH B  semantic     -> hybrid retrieve (BM25 + vector) over scene/query docs
   |                            -> top-k passages
   |
   v
[SYNTHESIS] grounded on Path A rows and Path B passages only; numeric check; citations
```

**Path A - the structured path.** The router compiles the question into a typed query object, never into raw SQL text from a model:

```python
class AnalyticsQuery(BaseModel):
    select: Literal["scenes","queries","traces"]
    filters: dict = {}                    # {"input_config":"BI_TEMPORAL","created_after":"2026-03-01"}
    group_by: list[str] = []              # ["place_label"] | ["month"] | ["task"]
    metric: Literal["count","distinct","sum_area_ha","mean_confidence","max"] = "count"
    metric_field: str | None = None
    order_by: str | None = None
    limit: int = Field(50, ge=1, le=500)
```

*"Which locations have I inspected up until now?"* compiles to `{select: "scenes", group_by: ["place_label"], metric: "count"}` and returns an exact, complete list plus the map pins for it. No embedding is involved, nothing is approximated, and nothing can be hallucinated because the answer is a query result. The compiled query is shown in the answer's "how this was computed" disclosure - the same auditability instinct as v1's execution trace, applied to recall.

**Path B - the semantic path.** Corpus documents, built from what already exists:

| Doc type | Built from | Text content |
|----------|-----------|--------------|
| `scene` | `scenes/{id}` | name, district labels, config, modalities, sensors, dates, compatibility summary |
| `query` | `queries/{id}` | the question, the answer, confidence band, abstention reason |
| `finding` | `traces/{id}` | one doc per tool step with a non-empty `facts` block: tool, key numbers, output summary |

Chunking is unnecessary - these are short. Retrieval is **hybrid**: BM25 (rank_bm25 locally, or Firestore keyword prefilter) intersected with vector top-k, then reciprocal-rank-fused. Pure vector search on a corpus this small and this proper-noun-heavy underperforms BM25 on exactly the queries users ask ("Nashik", "RISAT", "NDWI"), which is the standard result for small domain corpora and worth not rediscovering the hard way.

**Storage:** local dev uses `sqlite-vec` or a FAISS flat index rebuilt at startup - a workspace with 5,000 documents is milliseconds either way, and a flat index removes an entire class of stale-index bugs. Cloud uses Firestore documents plus the same in-memory index per instance, rebuilt on cold start from a single collection scan. Do not reach for a managed vector database at this corpus size; it adds a dependency, a cost line and a consistency problem in exchange for nothing measurable.

**Indexing triggers:** scene create/update/delete, query completion, and `POST /api/historical/reindex` for a full rebuild. Indexing is best-effort and asynchronous - a failed index write must never fail the query that triggered it.

**Synthesis and grounding.** Reuse v1 §9.6 verbatim. The synthesiser may only restate Path A rows and Path B passages; `verify_grounded()` runs against the union of retrieved facts, and on failure the answer falls back to a template rendering of the rows. Every claim carries citations, rendered as chips that deep-link to `/scene/{id}` or to the specific query's trace. An answer with no citations is a bug, and the UI should render it as one ("I could not find anything in your history that answers this") rather than as prose.

**Suggested prompts** in the composer: *"Which locations have I inspected?"* · *"Which scene had the largest changed area?"* · *"Summarise everything I've analysed in Maharashtra"* · *"Have I ever seen high abstention on SAR scenes?"*

## 9. F6 - Causal Reasoning

### 9.1 Purpose & surface

The user asks *"why did this change happen?"* The honest answer is that the system does not know - satellite imagery records what changed, not why. But the date range and the geographic bounds are known, and public reporting about that place in that window is searchable. If a flood was reported in the district on 27 June and the imagery shows a water-index spike between 20 June and 5 July, that is a defensible candidate explanation, and it is far more useful than "changes were detected".

Surface: right rail panel **Causal Reasoning** (`order: 600`), all scene types.

### 9.2 Independence contract

Needs from v1: the tool registry, stored `ToolResult.facts` from prior queries on this scene, the trace, the abstention treatment (§4.5). Needs from F0: right rail, `ChatComposer`, `AdminLookup`.
Must not need: F5 (both use `AdminLookup`, which is F0 infrastructure, not a feature); F4 (works on any scene type).
Optional interop: F4 (offer hypotheses per interval rather than per scene). Guarded.

### 9.3 The rule this feature lives under

> **This feature produces ranked candidate explanations with sources and match scores. It never asserts a cause.**

Concretely, in the UI and in every generated sentence:
- The heading is "Candidate explanations", not "Cause".
- Every hypothesis shows its score breakdown, so the user sees *why* it ranked where it did.
- Every hypothesis links out to its source and shows publisher and date.
- **A mandatory "alternative explanations" block** lists the non-event causes that would produce the same pixels: seasonal phenology, crop cycle, sensor geometry or incidence-angle difference, cloud or terrain shadow, co-registration error, atmospheric correction difference, and tide or reservoir operating level. This block appears even when a hypothesis scores highly.

The last point matters more than it looks. An NDVI drop between March and June in Maharashtra is much more likely to be a harvest than a deforestation event, and a system that reports the deforestation news story without naming phenology is actively misleading. Listing the boring explanation alongside the interesting one is the whole difference between an analytical tool and a rumour engine.

### 9.4 Pipeline

```
[1] scope      AOI bounds + date window from the scene
[2] place      AdminLookup.labels_for_bbox -> every intersecting district + state
[3] signature  read measured facts from this scene's stored ToolResults
[4] queries    event taxonomy x place x window -> search query set
[5] search     MCP client -> web search tool -> results
[6] extract    fetch + parse: publish date, place mentions, short summary
[7] score      temporal x spatial x signature x source -> ranked hypotheses
[8] present    candidates + score breakdown + alternatives + caveat
```

**Step 1 - scope.** Bi-temporal and multitemporal scenes give a real window (`t1.acquired_at` to `t2.acquired_at`). A single scene gets `acquired_at ± CAUSAL_SINGLE_SLACK_DAYS` (default 7), and the panel says so - a single observation cannot bound an event, and pretending otherwise would produce spurious matches.

**Step 3 - signature is what separates this from a news feed.** Read the scene's existing stored query results (v1 already persists `ToolResult.facts` in `queries/{id}` and `traces/{id}`) and extract the measured direction of change:

```python
EVENT_SIGNATURES = {
    "flood":        {"ndwi": "+", "backscatter_land": "-", "ndvi": "-", "extent": "contiguous"},
    "drought":      {"ndwi": "-", "ndvi": "-", "seasonal": True},
    "wildfire":     {"ndvi": "-", "nbr": "-", "extent": "patchy"},
    "cyclone":      {"ndvi": "-", "ndwi": "+", "extent": "broad"},
    "landslide":    {"ndvi": "-", "extent": "linear_steep"},
    "deforestation":{"ndvi": "-", "ndbi": "0", "extent": "blocky", "persistent": True},
    "mining":       {"ndvi": "-", "ndbi": "+", "extent": "blocky"},
    "construction": {"ndbi": "+", "ndvi": "-", "extent": "blocky"},
    "reservoir_ops":{"ndwi": "±", "extent": "shoreline"},
    "harvest":      {"ndvi": "-", "seasonal": True, "extent": "field_parcel"},
}

def signature_agreement(event: str, measured: dict) -> float:
    """0-1. Absent measurements score 0.5 (neutral), not 1.0 - a hypothesis
    cannot earn credit from evidence that was never gathered."""
```

A flood story scores high only if the measurements actually show a water-index increase. A flood story against a scene whose NDWI *fell* gets scored down and stays visible with its low score and the disagreement stated - which is more useful than hiding it, because a user who knows there was a flood learns that their imagery does not show it, which is itself a finding.

If the scene has no prior measurement results, the panel offers a one-click "run the measurements first" that submits an appropriate query to v1's controller, then re-scores. Do not run hypotheses against nothing.

**Step 4 - query construction.** Templated per event type over every intersecting district:

```python
TEMPLATES = [
    "{district} {state} {event_term} {month} {year}",
    "{district} {event_term} news {year}",
    "{state} {event_term} {district} report",
]
```
Cap at `CAUSAL_MAX_QUERIES` (default 12) per invocation across all districts and events, prioritised by signature agreement - search the events the measurements support first, so the quota buys relevant results.

**Step 5 - MCP client.**

```python
# backend/features/causal/mcp_client.py
class MCPSearchClient:
    """Speaks MCP to a search server (e.g. a DuckDuckGo MCP server) over stdio or HTTP.
    Tools are discovered at connect time; the client binds to whatever search-shaped
    tool the server advertises rather than hardcoding a tool name."""
    async def connect(self) -> list[MCPTool]: ...
    async def search(self, query: str, max_results: int = 8) -> list[SearchHit]: ...
    async def fetch(self, url: str) -> str | None: ...     # if the server offers fetch
```

Configuration is transport-agnostic (`MCP_SEARCH_TRANSPORT=stdio|http`, `MCP_SEARCH_SERVER_CMD`, `MCP_SEARCH_SERVER_URL`). DuckDuckGo is the default because it needs no API key, which keeps the feature installable; any MCP search server that advertises a search tool is a drop-in swap. If the server is unreachable at startup, the panel reports "search backend unavailable" and the tool declares itself unavailable to the input gate - v1 §7.2's exact pattern for GEE, reused rather than reinvented.

**Step 6 - extraction, and the rule that governs it.** For each hit, record `url`, `title`, `publisher`, `published_at`, and a **short extractive summary of at most two sentences**. Do not store or display article bodies, and always link out. This is a search-and-cite feature, not a content mirror; a system that reproduces news copy into a PDF report creates a licensing problem for the user that they did not ask for.

**Step 7 - scoring.**

```python
def score(hit: SearchHit, event: str, scope: CausalScope, measured: dict) -> Hypothesis:
    temporal = date_overlap_score(hit.published_at, scope.window)      # 1.0 inside, decaying ±30d
    spatial  = place_match_score(hit, scope.districts)                 # district > state > national
    signature= signature_agreement(event, measured)
    source   = source_credibility(hit.publisher)                       # gov/IMD/NDMA > major outlet > aggregator > unknown
    total = (0.30*temporal + 0.25*spatial + 0.35*signature + 0.10*source)
    return Hypothesis(event=event, score=round(total,3),
                      breakdown={"temporal":temporal,"spatial":spatial,
                                 "signature":signature,"source":source},
                      evidence={"news":[hit], "measurements": relevant_facts(measured, event)},
                      caveat=CAVEATS[event])
```

Signature carries the largest weight deliberately: a measurement made from the user's own imagery is stronger evidence than a headline. Hypotheses below `CAUSAL_MIN_SCORE` (default 0.35) are collapsed under "lower-confidence candidates", not deleted.

**Step 8 - registered as a tool**, so causal reasoning inherits the trace, the confidence aggregation, the parameter whitelist and the abstention path for free:

```python
class CausalSearchParams(ToolParams):
    event_types: list[str] = Field(default_factory=lambda: list(EVENT_SIGNATURES), max_length=13)
    max_results_per_query: int = Field(8, ge=1, le=20)
    slack_days: int = Field(7, ge=0, le=60)

@register
class CausalSearchTool(Tool):
    name = "causal_search"
    description = ("Search public reporting for events in the scene's area and date window "
                   "that could explain observed change. Returns ranked candidate "
                   "explanations with sources. Does not establish causation.")
    accepts = ["SINGLE","CROSS_MODAL","BI_TEMPORAL","MULTITEMPORAL"]
    produces = ["text","stats"]
    offline_capable = False
```

### 9.5 UI specification

- **Scope header**: the resolved districts, the date window, and where it came from ("t1 → t2" or "acquisition ± 7 days"), all editable before running. Editing the window re-runs; the search is cheap relative to being wrong about scope.
- **Event filter**: chips for the taxonomy, all on by default, with the signature-agreement score shown per chip after a run so the user can see which event types the imagery actually supports.
- **Hypothesis cards**, ranked: event label, score bar with the four-part breakdown on hover, the two-sentence summary, publisher + date + outbound link, and a "measurements that support / contradict this" expander pulling the actual numbers from prior tool results.
- **Alternative explanations block**, always rendered, never collapsed by default.
- **Standing caveat**, always visible: *"These are candidate explanations found in public reporting for this area and period. Temporal and spatial coincidence is not causation."*
- **Chat composer** for follow-ups ("what about the reservoir upstream?"), which re-scopes and re-runs rather than free-associating.

### 9.6 Caching & rate limits

Search quota is finite and the same AOI gets asked repeatedly. Cache keyed by `(rounded_bbox, window, event_type)` with a 24-hour TTL; show a "cached, N hours ago" chip with a refresh button. Per-workspace rate limit `CAUSAL_MAX_QUERIES_PER_HOUR` (default 60). Back off and surface the wait rather than failing.

### 9.7 Failure & degradation

| Condition | Behaviour |
|-----------|-----------|
| MCP server unreachable | Panel shows the backend as unavailable; the tool reports a missing capability through v1's input gate, not a crash |
| No search results | Say so plainly. Then **still show the signature analysis** - "the measurements indicate a water-extent increase consistent with flooding, but no public reporting was found for this district in this window" is a genuinely useful answer |
| Remote or sparsely-reported AOI | Expect this to be common. The empty-result copy should name it: rural Indian districts frequently have no indexed English-language reporting, and absence of news is not absence of event |

| Single-image scene | Works, with the slack window and an explicit note that a single observation cannot bound an event |

## 10. F7 - 3D Terrain & Street View

### 10.1 Purpose & surface

Let the analyst leave the flat overhead view: see the scene's own imagery draped over real terrain, and get present-day ground-level and photorealistic context for the same coordinates.

Surface: right rail panel **3D & Street View** (`order: 700`), all scene types.

### 10.2 The correction that has to be stated up front

The instruction for this feature was to render 3D and Street View using Google Earth Engine. **Earth Engine does not do either.** GEE is a raster catalogue and a distributed analysis engine; it serves elevation models and imagery, and it has no photorealistic 3D renderer and no Street View. Photorealistic 3D Tiles and Street View are **Google Maps Platform** products, which are separately billed and separately keyed.

Rather than word-game that, split the feature into two honestly-labelled modes - which turns out to be the better product anyway:

| Mode | Data | Date-accurate to the scene? | Cost |
|------|------|----------------------------|------|
| **10.4 (A) Terrain 3D** | GEE DEM (SRTM / Copernicus GLO-30) + **the user's own scene imagery as texture** | **Yes** - the texture is their raster from their acquisition date | GEE quota only |
| **10.5 (B) Contextual 3D & Street View** | Maps Platform Photorealistic 3D Tiles, Street View | **No** - present-day Google imagery | Paid per session/request |

Mode A is the one that actually satisfies the intent: 3D of the bounds, within the dates the user gave at scene creation, because it is literally their pixels on real elevation. Mode B is context, and it must be banner-labelled as present-day. In v1's own spirit (§7.0), record the trade-off here so nobody re-derives it under deadline pressure and quietly mislabels Mode B as date-matched.

### 10.3 Independence contract

Needs from v1: `Scene.bounds_wgs84`, the preview PNG, `core/gee.py`. Needs from F0: right rail.
Must not need: F1, F2.
Optional interop: F1 (use the enhanced preview as the texture - a super-resolved drape looks dramatically better at oblique angles); F2 (drape annotation layers onto the terrain). Both guarded; absent means the raw preview and no annotation overlay.

### 10.4 (A) Terrain 3D from the scene's own raster

**Backend** - `POST /api/scenes/{id}/terrain` runs once per scene and caches:

```python
async def build_terrain(scene: Scene, cfg: TerrainConfig) -> TerrainAsset:
    aoi = ee.Geometry.Rectangle(scene.bounds_wgs84())
    dem = (ee.Image("COPERNICUS/DEM/GLO30").select("DEM")
           if cfg.dem == "glo30" else ee.Image("USGS/SRTMGL1_003"))
    # Downsample to a mesh-sized grid. 512x512 is 262k vertices - plenty for
    # terrain at AOI scale, and it keeps the payload under ~2 MB.
    grid = dem.clip(aoi).reproject(crs="EPSG:4326", scale=cfg.mesh_scale_m)
    heights = sample_to_array(grid, aoi, cfg.mesh_size)          # float32 [N,N], metres
    return TerrainAsset(
        elevation_path=write_npz(heights),
        mesh_size=cfg.mesh_size,
        bounds_wgs84=scene.bounds_wgs84(),
        extent_m=(width_m(aoi), height_m(aoi)),   # for honest 1:1 exaggeration
        z_min=float(heights.min()), z_max=float(heights.max()),
        dem_source=cfg.dem, dem_gsd_m=30.0,
    )
```

**Frontend** - three.js via react-three-fiber:
- `PlaneGeometry(mesh_size-1, mesh_size-1)` displaced along Z by the elevation array
- The scene preview (enhanced if F1 is on) as the texture, `ClampToEdgeWrapping`, anisotropy at the device max
- **Honest scale at 1×**: convert elevation metres into the same world units as the AOI's ground extent, so a 1× exaggeration is genuinely 1:1. Most terrain viewers silently exaggerate; label the slider `1×` through `5×` and default to `1.5×` with the number always visible
- Orbit / pan / zoom; a `Home` reset; a compass rose that stays north-up-correct
- Sun azimuth and elevation sliders driving a directional light, so the user can rake light across the surface - the single most effective way to reveal subtle topographic structure
- Toggles: wireframe, contour lines (10/50/100 m), and **evidence drape** - any `EvidenceLayer` PNG from a query on this scene, and any F2 annotation layer, composited onto the texture. A change mask draped over terrain is the most legible visualisation this product can produce
- Click-to-inspect: raycast to the surface, return lat/lon/elevation in a readout, with buttons "start an annotation here" (if F2) and "ask about this point" (seeds the query console with the coordinates)

**Why DEM resolution must be stated.** GLO-30 and SRTM are 30 m. A 2 m Cartosat scene draped on a 30 m DEM will have crisp imagery on smooth terrain, and buildings will not stand up - because a 30 m DEM is a *terrain* model, not a surface model. Put that in the panel as a one-line note. Users who expect extruded buildings need Mode B, and telling them why is faster than letting them conclude the feature is broken.

### 10.5 (B) Contextual 3D & Street View

**Photorealistic 3D Tiles**: `https://tile.googleapis.com/v1/3dtiles/root.json` rendered with `3d-tiles-renderer` in the same three.js canvas, camera initialised over the AOI centroid. A persistent banner: *"Contextual view. This is present-day Google imagery, not your scene's acquisition."*

**Street View**: check coverage before rendering anything.

```typescript
// Coverage is sparse outside urban corridors. Always metadata-first -
// the metadata endpoint is free, and a failed embed looks like a broken feature.
const meta = await fetch(`https://maps.googleapis.com/maps/api/streetview/metadata?location=${lat},${lng}&key=${KEY}`);
if ((await meta.json()).status !== 'OK') return { covered: false };
```

Panel behaviour: sample the AOI centroid plus a small grid of candidate points, show the covered ones as pins on a mini-map, and open the embedded panorama for a selected pin. When nothing is covered - which will be the normal case for rural and remote AOIs - say exactly that: *"No Street View coverage within this AOI. Coverage is concentrated along roads and urban areas."*

**Cost and data-handling notes, both mandatory.** Maps Platform 3D Tiles and Street View are billed per session and per request; gate Mode B behind `FEATURE_GEO3D_MAPS_ENABLED` (separate from the feature flag), enforce a per-workspace daily cap, and show remaining quota in the panel. And note, in the same register as v1 §7.0's disclosure about preview pixels going to a hosted VLM: **Mode B transmits AOI coordinates to Google Maps Platform.** Confirm that is acceptable under the applicable data-handling rules before enabling it for a demo involving real operational AOIs. Mode A sends only a bounding box to GEE, which the product already does throughout.

### 10.6 Failure & degradation

| Condition | Behaviour |
|-----------|-----------|
| Scene not georeferenced | Panel gated: no bounds, no DEM, no coordinates. Structured refusal with the GeoTIFF remedy |
| GEE unavailable | If a cached `terrain.npz` exists, Mode A still renders from cache. Otherwise fall back to a locally-computed 2.5D hillshade of the raster itself - no elevation, but shape - and label it as such |
| WebGL unavailable / context lost | Static hillshade image plus a message; never a blank canvas |

| Very large AOI | DEM sampling is capped by `mesh_size`; the panel states the effective terrain resolution rather than silently coarsening |

## 11. F8 - Voice Input Across Chat Surfaces

### 11.1 Purpose & surface

Add a microphone to every chat interface in the product and let the user dictate their query. A field officer holding a tablet in a flood-affected district is not going to type *"has the built-up area within this polygon increased since March 2024"*.

Surface: an accessory button inside `ChatComposer`, which means it appears in v1's query console, F3's temporal-fetch chat, F5's RAG assistant, F6's causal follow-ups, and any chat surface added later - without those features knowing F8 exists.

### 11.2 Independence contract

Needs from F0: `ChatComposer`'s `accessories` slot. Needs from v1: nothing.
Must not need: F3, F5, F6. F8 must be demonstrable with only v1's query console present.
Interop direction is inverted here and worth noticing: **other features do not opt into F8; F8 opts into them**, by mounting into a slot they all already use. That is why `ChatComposer` is in F0 rather than in any feature.

### 11.3 Two backends behind one hook

```typescript
export type SpeechBackend = 'web' | 'server';

export function useSpeechInput(opts: {
  backend?: SpeechBackend | 'auto';
  language?: string;                       // BCP-47, default from settings
  mode?: 'toggle' | 'push';
  onInterim: (text: string) => void;
  onFinal:   (text: string) => void;
  onError:   (e: SpeechError) => void;
}): {
  state: 'idle' | 'requesting' | 'listening' | 'transcribing' | 'error';
  level: number;                           // 0-1 input level, for the waveform
  start(): void; stop(): void; cancel(): void;
};
```

| Backend | How | Pros | Cons |
|---------|-----|------|------|
| `web` | Web Speech API (`SpeechRecognition`) | Free, zero upload, low latency, interim results | Chrome/Edge only; absent in Firefox; quality varies; on some platforms audio still goes to a cloud service |
| `server` | `MediaRecorder` -> 16 kHz mono -> `POST /api/speech/transcribe` -> faster-whisper (`small` or `medium`) | Works in every browser, **runs fully offline with local weights**, much better on Indian-English and code-switched speech, glossary-conditionable | Higher latency (1-3 s), needs the model on disk, CPU cost |

`auto` resolves to `web` when `window.SpeechRecognition || window.webkitSpeechRecognition` exists, otherwise `server`. Deployments that must not send audio anywhere set `NEXT_PUBLIC_SPEECH_BACKEND=server` with a local whisper - which also happens to be the only configuration that satisfies v1 Design Rule 3's offline posture.

### 11.4 Interaction design

**States**, all four visually distinct on the mic button: idle (outline mic) · listening (filled, pulsing ring, live amplitude waveform) · transcribing (spinner) · error (amber mic with a slash, tooltip carries the reason).

**Modes**: click to toggle, or press-and-hold for push-to-talk. Push-to-talk is the better mode in the field and on mobile; make it the behaviour when the pointer is held for more than 400 ms.

**Interim transcript** streams into the textarea in a muted colour with the caret at the end. On finalisation it commits as ordinary editable text.

> **Never auto-submit.** The transcript lands in the composer and the user presses send. A misheard query that auto-runs is not just wrong - in this product it can spend a multi-minute GEE export or a paid VLM call on a question nobody asked. Dictation ends at the text box.

`Esc` cancels and discards the interim text; the previously typed content is restored, not clobbered.

**Permissions**: request the microphone on the first click, never on page load, and show a one-line rationale first. On denial, the button goes to error state with a link to browser permission settings. On a page with no secure context (`http://` other than localhost), disable with "microphone requires HTTPS".

**Language**: selector in the composer's mic menu and in Settings, defaulting to `en-IN`, with `hi-IN`, `mr-IN`, `bn-IN`, `ta-IN` and `en-US` available. Persist per user.

### 11.5 Domain vocabulary correction

General-purpose speech recognition mangles remote-sensing vocabulary in predictable ways, and a query console that reliably hears "and DVI" instead of "NDVI" will not be used twice.

```python
# Applied to the final transcript on both backends. Ordered, longest-first,
# word-boundary anchored, case-insensitive.
GLOSSARY_FIXES = [
    (r"\band\s+d\s*v\s*i\b",           "NDVI"),
    (r"\bn\s+d\s+w\s+i\b",             "NDWI"),
    (r"\b(and|n)\s*d\s*b\s*i\b",       "NDBI"),
    (r"\bsentinel\s+(one|1)\b",        "Sentinel-1"),
    (r"\bsentinel\s+(two|2)\b",        "Sentinel-2"),
    (r"\bcarto\s*sat\b",               "Cartosat"),
    (r"\bre\s*sat\b|\bri\s*sat\b",     "RISAT"),
    (r"\bbhoo\s*nidhi\b",              "Bhoonidhi"),
    (r"\bsar\b",                       "SAR"),
    (r"\bby\s+temporal\b",             "bi-temporal"),
    (r"\bgeo\s*tiff\b",                "GeoTIFF"),
    (r"\bbuilt\s+up\b",                "built-up"),
]
```

On the server path, additionally seed whisper's `initial_prompt` with the glossary ("Remote sensing analysis. Terms: NDVI, NDWI, NDBI, SAR, Sentinel-1, Sentinel-2, Cartosat, RISAT, GeoTIFF, bi-temporal, co-registration, backscatter, land cover.") - conditioning the decoder is more effective than post-hoc correction, and the two together cover most of it. Keep the map in one module so both paths share it.

### 11.6 Privacy & accessibility

- **Audio is never persisted.** `SPEECH_RETAIN_AUDIO=false` is the default and the server discards the buffer after transcription. If a deployment enables retention for debugging, the composer shows a recording-retained indicator - not a settings-page footnote.
- If the server path is configured to a third-party STT rather than a local model, state the provider in Settings. Same disclosure standard v1 §7.0 applies to the VLM.
- **Voice is never the only path.** Every action reachable by dictation is reachable by typing. The mic button is keyboard-focusable and operable with `Space`; state changes are announced through `aria-live="polite"`; the waveform has a text equivalent ("listening").

### 11.7 Failure & degradation

| Condition | Behaviour |
|-----------|-----------|
| No `SpeechRecognition` and no server backend configured | Mic hidden entirely. Typing is unaffected; nothing is broken, one affordance is absent |

## 13. F10 - Autonomous Monitor

### 13.1 Purpose & surface

Standing questions that should be answered without anyone asking: *"tell me when flood coverage crosses 50% of these bounds"*. A monitor is an AOI, a schedule, a metric, a threshold and an action. It pulls fresh imagery on a cadence, measures, compares, and fires.

Surface: left nav **Autonomous Monitor** (`order: 550`), route `app/monitor/page.tsx`.

### 13.2 Independence contract

Needs from v1: the deterministic tools (`spectral_index`, `sar_water_mask`, `geo_stats`), the scene creation path, `ExecutionTrace`. Needs from F0: left nav, `ImagerySource`.
Must not need: F9 or F11. Both touch adjacent territory (reports; district-based AOIs) and neither is required.
Optional interop: F9 (`generate_report` as an alert action); F11 (reuse a live-pull AOI as a monitor AOI, passed as plain bounds, not as a function call).

### 13.3 Hosting: define the contract, not the platform

There is no scheduler host provisioned yet. That is fine - the correct response is to make the runner **host-agnostic and idempotent**, so whichever scheduler appears later works without changing a line of application code.

> **The entire scheduling surface is one function:** `run_due_monitors(now: datetime) -> RunSummary`.

Four ways to drive it, all supported, none preferred by the code:

| Driver | Setup | Suits |
|--------|-------|-------|
| `POST /api/monitors/tick` with a shared secret | GitHub Actions `schedule:`, cron-job.org, an EC2 crontab, a laptop | Now, with zero infrastructure |
| Cloud Scheduler -> Cloud Run Job | `gcloud scheduler jobs create http monitor-tick --schedule="*/15 * * * *"` | The v1 deployment target (§17), when it exists |
| `python -m jobs.monitor_runner --loop --interval 900` | Local process | Development and demos |
| **Run now** button | Manual | Testing a monitor without waiting for its cadence |

Requirements the runner must satisfy regardless of driver - these are the properties that make the host swappable:

1. **Idempotent.** Calling it twice for the same window produces one run and one alert, not two.
2. **Leased.** A due monitor is claimed with a lease token and a 15-minute TTL before any work. Two concurrent ticks cannot double-fire, which matters because the naive cron setups above will occasionally overlap.
3. **Stateless.** All state lives in the monitor document. The runner holds nothing between invocations.
4. **Bounded.** Each invocation finishes within `MONITOR_TICK_BUDGET_SECONDS` (default 540, under a typical 10-minute platform limit); monitors not reached are simply due on the next tick.
5. **Catch-up, not backfill.** If three ticks were missed, run the monitor **once** against current imagery. Nobody wants three identical flood alerts because a scheduler was down overnight.
6. **Self-limiting.** `max_runs_per_day` per monitor and a workspace-wide quota, both enforced in the runner rather than trusted to the scheduler.

### 13.4 Monitor model

```python
class MonitorCondition(BaseModel):
    metric: Literal["water_fraction","ndvi_mean","ndbi_fraction","changed_fraction",
                    "backscatter_mean","cloud_fraction"]
    op: Literal["gt","lt","crosses_above","crosses_below","delta_gt","delta_lt"]
    value: float
    baseline: Literal["none","first_run","rolling_7d","rolling_30d","fixed_date"] = "none"
    baseline_date: date | None = None
    consecutive_required: int = Field(2, ge=1, le=5)

class MonitorAction(BaseModel):
    kind: Literal["in_app","email","webhook","create_scene","generate_report"]
    target: str | None = None
    payload_template: str | None = None

class Monitor(BaseModel):
    id: str; workspace_id: str; name: str; enabled: bool = True
    aoi: BBox
    aoi_label: str | None = None
    source: Literal["gee_s2","gee_s1","bhoonidhi"]
    max_cloud: float = Field(40.0, ge=0.0, le=100.0)
    schedule: str                      # cron expression
    timezone: str = "Asia/Kolkata"
    condition: MonitorCondition
    actions: list[MonitorAction]
    cooldown_hours: int = Field(24, ge=1, le=720)
    max_runs_per_day: int = Field(4, ge=1, le=24)
    state: MonitorState
```

**Conditions are typed, never free text.** Natural-language rule entry is offered in the UI - the user types *"let me know when flood coverage crosses 50% of these bounds"* - but it is **compiled** into the struct above and **shown back for confirmation before saving**:

> Compiled to: metric `water_fraction`, operator `crosses_above`, value `0.50`, baseline `none`, requires `2` consecutive breaches, cooldown `24 h`.

An alert rule has to be deterministic, re-evaluable and auditable months later. A stored sentence is none of those. Compile, confirm, store the struct - and keep the original sentence alongside it for display.

### 13.5 Runner

```python
async def run_due_monitors(now: datetime) -> RunSummary:
    for mon in lease_due_monitors(now, limit=MONITOR_BATCH, ttl_s=900):
        try:
            # 1. Has anything new been acquired? If not, don't spend the compute.
            candidates = imagery.search(mon.aoi, since=mon.state.last_asset_time,
                                        until=now, max_cloud=mon.max_cloud)
            if not candidates:
                record_run(mon, status="SKIPPED_NO_NEW_DATA"); continue

            tile = await imagery.fetch(mon.aoi, [candidates[0].asset_id], ...)

            # 2. Optical metrics are meaningless under cloud. Refuse, don't guess.
            if is_optical(mon.source) and tile.cloud_fraction > mon.max_cloud / 100:
                record_run(mon, status="SKIPPED_CLOUD",
                           note=f"cloud {tile.cloud_fraction:.0%} over AOI"); continue

            # 3. Deterministic tools only. No VLM, no LLM, in the alerting path.
            value = compute_metric(mon.condition.metric, tile)
            fired, reason = evaluate(mon.condition, value, mon.state)

            run = record_run(mon, status="OK", value=value, tile=tile, fired=fired)
            if fired and not in_cooldown(mon, now):
                await dispatch(mon, run, reason)
        except Exception as e:
            record_run(mon, status="FAILED", error=str(e))
            backoff(mon)          # disable after MONITOR_MAX_FAILURES consecutive failures
        finally:
            release_lease(mon)
    return summary
```

Three decisions in that function are worth defending explicitly:

- **Skip when there is no new acquisition.** Sentinel-2 revisits every ~5 days; a daily monitor would otherwise re-measure the same image four times and burn quota to reach the same answer. Comparing catalogue timestamps costs one cheap search call.
- **Skip under cloud, never evaluate through it.** Cloud over water indices reads as bright, non-water surface; cloud shadow reads as dark, water-like surface. An optical flood monitor that evaluates through 70% cloud will produce both false alarms and false silences. `SKIPPED_CLOUD` is a first-class outcome shown in the run log, and the panel suggests adding a Sentinel-1 monitor for the same AOI - which is the same cross-modal argument the product already makes.
- **Deterministic tools only in the alerting path.** An alert must be reproducible and explainable at 3 a.m. and must not cost a VLM call per tick. The imagery is materialised as a scene, so a user who wants a description can ask the full agent afterwards - with a trace.

**Hysteresis.** `crosses_above` fires on a transition from below to above, not on every run while above. Plus `consecutive_required` (default 2) so one anomalous acquisition does not page anyone, plus `cooldown_hours` before re-firing. Together these are the difference between a monitor and a noise source.

### 14.1 Purpose & surface

### 14.2 Independence contract

Needs from v1: the standard ingest path (`POST /api/scenes/confirm`) and everything downstream of it. Needs from F0: left nav, `ImagerySource`, `AdminLookup`.
Must not need: F10 or F3.

### 14.3 District resolution

Typeahead over `AdminLookup.search()`, with state always shown because Indian district names collide (Aurangabad in Maharashtra and in Bihar; Hamirpur in UP and in Himachal Pradesh; Bilaspur in three states). Results render as `District, State` and the selection stores `unit_id`, never the bare name.

Also accept: a dropped pin on a map, pasted bounds, or a pasted lat/lon. District name is the primary path because it is the one a person can do from memory in the field.

### 14.4 AOI construction, done correctly

The user picks a target area from chips - **10 · 50 · 100 · 250 km²** - or types a custom value up to `LIVE_MAX_AREA_KM2`.

A naive implementation builds a square in degrees around the centroid. That is wrong: a degree of longitude at 20°N is about 105 km while a degree of latitude is about 110 km, so a "square" degree box is a rectangle, and its area is off by the cosine of the latitude. Build the AOI in a projected CRS instead:

```python
def build_aoi(centroid: tuple[float, float], area_km2: float) -> tuple[BBox, str]:
    """Square AOI of exactly `area_km2`, constructed in the local UTM zone
    so the area is real rather than a degree approximation."""
    lon, lat = centroid
    utm = utm_crs_for(lon, lat)                       # EPSG:326xx / 327xx
    to_utm   = Transformer.from_crs("EPSG:4326", utm, always_xy=True)
    to_wgs   = Transformer.from_crs(utm, "EPSG:4326", always_xy=True)
    cx, cy = to_utm.transform(lon, lat)
    half = (area_km2 ** 0.5) * 1000 / 2               # metres
    corners = [(cx-half, cy-half), (cx+half, cy+half)]
    (w, s), (e, n) = [to_wgs.transform(x, y) for x, y in corners]
    return BBox(w, s, e, n), utm
```

Two AOI shapes offered: **square** (centred on the district centroid, exact area) or **clip to district** (the district polygon itself, with its true area shown - which is often far larger than 250 km² and must therefore be capped or refused with the number stated).

Render the resulting footprint on a Leaflet preview with the computed area, the UTM zone, and an estimated download size **before** anything is fetched. A user should never be surprised by what arrives.

### 14.5 Source selection and the composite decision

- **Sentinel-2 L2A** (optical, 10 m) · **Sentinel-1 GRD** (SAR, ~10 m) · **both** -> creates a `CROSS_MODAL` scene, which drops the user straight into v1's cross-modal path (R6) with real data. That is the strongest possible live demo, and it costs one extra checkbox.
- Date window: last 30 days by default, adjustable.
- Cloud threshold slider, default ≤ 20%.
- Compositing choice, and it must be an explicit choice:

| Option | What it is | When |
|--------|-----------|------|
| **Single acquisition** | One real observation on one real date | Default. Honest, and change detection against it means something |
| **Cloud-masked median composite** | A statistic over the window | Offered when no single acquisition is under the cloud threshold - which in a monsoon month is most of them |

A composite is not an observation. Set `ImageryTile.composite=true`, store the window rather than a date, label it in the scene name and metadata, and carry the label into every trace and report (extension Design Rule 2). The UI states the difference once, at the point of choice, in one sentence.

**Preflight is mandatory.** Show the candidate acquisitions (date, cloud %, tile id, orbit, relative orbit for S1) and let the user choose. The same rule as F3 §6.6, for the same reason: a silent mystery composite is the fastest way to lose a user's trust in a system whose entire proposition is grounded answers.

### 14.6 Fetch, materialise, run

```
[1] resolve district        -> unit_id, centroid, polygon
[2] build AOI               -> bbox in local UTM, area verified
[3] search                  -> candidates per collection
[4] user selects            -> acquisition(s) or composite
[5] export                  -> getDownloadURL (<50 MB) or batch export, polled
[6] normalise               -> reproject to the AOI's UTM zone, 10 m, GeoTIFF
[7] ingest                  -> POST /api/scenes/confirm  (v1's standard path, untouched)
[8] run                     -> suggested queries, streamed through v1's controller
```

Step 7 is the whole design. Nothing after it is F11's code.

**Provenance** on the created scene: `{"kind": "live_pull", "collection": ..., "asset_ids": [...], "acquired": ..., "composite": bool, "cloud_fraction": ..., "admin_unit": "IN-MH-PUNE", "admin_vintage": "...", "aoi_km2": 50.0, "utm": "EPSG:32643"}`. Scene name defaults to `Pune, Maharashtra · S2 · 2026-08-28 · 50 km²`.

**Step 8** offers a suggested query set appropriate to what was pulled, extending v1 §4.5's `SuggestedQueries` pattern:
- S2 only: *"Describe the land cover in this area"* · *"Where is the water?"* · *"How much of this area is built-up?"*
- S1 only: *"Identify water bodies from the SAR backscatter"*
- Both: *"Use the optical and SAR images together to identify built-up and water-covered regions"* - v1's own cross-modal demo line (§16), now on live data

| Guardrail | Default | Why |
|-----------|---------|-----|

## 19. Verification: Independence Tests & Definition of Done

### 19.1 There is no implementation order

Deliberately. Pick any feature, build it, ship it. The only prerequisite anywhere in this document is F0, which is roughly a day's work and is shared by everything.

If several developers are working at once, the natural split is: one on F0 first (unblocking everyone), then one developer per feature with no coordination required beyond agreeing on `order` bands (3.1) - and those are already assigned.

If a demo date forces a choice, the highest visible impact per unit of work is F2 (annotations are the most immediately impressive thing in the list), F11 (proves the system on unseen data, which is the question every evaluator asks), and F4 (the animated stack is the best-looking thirty seconds in the product). That is a suggestion for prioritisation, not a dependency chain - none of the three needs either of the others.

### 19.2 Independence test suite

These run in CI on every push and are the executable form of section 1.2.

```yaml
# .github/workflows/independence.yml
jobs:
  each-feature-alone:
    strategy:
      matrix:
        feature: [enhancement, annotation, temporal_fetch, stack, historical,
                  causal, geo3d, voice, reports, monitor, live]
    steps:
      # Exactly one feature on. Build, boot, smoke-test that feature and all of v1.
      - run: |
          export FEATURE_${{ matrix.feature | upper }}_ENABLED=true
          pytest backend/tests -q
          npm --prefix frontend run build
          pytest backend/tests/smoke/test_v1_unchanged.py -q

  all-features-off:
    # The regression that matters most: v1 must be exactly v1.
    steps:
      - run: pytest backend/tests -q && npm --prefix frontend run build
      - run: pytest backend/tests/smoke/test_v1_unchanged.py -q

  all-features-on:
    steps:
      - run: pytest backend/tests -q

  no-cross-feature-imports:
    steps:
      - run: npm --prefix frontend run lint
      - run: pytest backend/tests/test_independence.py -q

  offline-eval-still-passes:
    # v1 §17.14's existing check. New tools declare offline_capable; the offline
    # path must still complete with --network none.
    steps:
      - run: |
          docker build -t satquery-eval -f eval/Dockerfile .
          docker run --network none satquery-eval \
            python -m eval.run_benchmark --dataset smoke --limit 5 --planner-backend local
```

The `each-feature-alone` matrix is the important one. Eleven jobs, each proving that one feature works with nothing else present. If a feature only passes when another is on, the coupling is real and the design has drifted - fix it before merge, not after.

### 19.3 Cross-cutting acceptance criteria

Independent of any single feature, all of the following must hold on a build with everything enabled:

- [ ] Every new analytical capability appears in `GET /api/tools` and in the `ExecutionTrace` (extension Design Rule 4)
- [ ] Every new chat surface passes v1 §9.6's numeric grounding check; a forced bad synthesis falls back to template rendering (Rule 5)
- [ ] Every fetched, composited or enhanced artifact carries `provenance` and is labelled in the UI, the trace and every report (Rule 2)
- [ ] `geo_stats` returns identical measurements with F1 on and off, on the same scene (Rule 1) - this is a numeric assertion, not a visual check
- [ ] F6 never emits a causal assertion; the alternative-explanations block is present in every response (Rule 3)
- [ ] The right rail renders all registered panels in reserved-band order with no collisions
- [ ] v1's offline evaluation path (§11.5) completes unchanged with `--network none`
- [ ] v1's existing demo script (§16) runs end to end with every feature enabled and produces the same answers

### 19.4 Demo additions

v1 §16 has a seven-step demo script. These slot in without disturbing it - each is independent, so any subset can be shown depending on what is built:

1. **Live pull (F11)** - type "Nashik", pick 50 km², pull today's Sentinel-2 and Sentinel-1, and run v1's own cross-modal demo line on data nobody has seen. This is the strongest opener because it removes the "prepared sample" objection in the first thirty seconds.
2. **Annotate and measure (F2)** - circle a region, ask "how much of this is water", get an exact hectare figure from a deterministic mask. Then ask "where else is there water" and watch the agent draw its own polygon layer back.
3. **Stack (F4)** - drop five dates, watch them stack oldest-to-newest, scrub the timeline, play the change animation, read the trajectory chart.
4. **Single to bi-temporal (F3)** - one image, one sentence, a fetched second date, a change answer with a full trace.
5. **Causal (F6)** - "why did this change?" -> ranked candidates with a flood report matching both the date window and the measured water-index increase, and the alternative-explanations block sitting right underneath it. The candour is the point.
6. **3D (F7)** - drape the change mask over terrain and orbit it.
7. **Historical (F5)** - "which locations have I inspected?" answered exactly, with map pins and clickable citations.
8. **Report (F9)** - download the activity report and turn to the provenance page, which states plainly what ran, what was fetched, what was composited, and that nothing was fine-tuned.

Steps 5 and 8 are the ones that make an evaluator trust the rest. Do not cut them for time.
